# Health ID interface simplification audit

Date: 2026-10-03. Status: **audit and proposed design only — awaiting approval**.

Source: [the supplied brief](UI-SIMPLIFICATION-SPEC.md). Its instruction is: “Produce the audit first … and wait for my approval before large restructuring.” No application interface, permission or workflow changes were made in this audit turn.

## Coverage and existing system

- 33 catalogue modules and 16 account roles extracted from the actual TypeScript catalogue/model into [source inventory](artifacts/ui-source-inventory.json).
- Shared hash routing and one workspace shell in `src/app.tsx`; most list/create/detail/action screens use `src/workflows.tsx` with catalogue fields/transitions.
- Six registration provider categories and eight legacy setup types. They are not a single taxonomy. Pharmacy registration currently maps to the internal Clinic type.
- Existing `can`/`requirePermission` checks combine membership, role permissions, extra/denied permissions, selected branch departments and facility verification. Provider type is not currently a navigation/access filter. There is no independent enabled-module registry.
- Existing Button, Card, Heading, Form, PasswordInput, Badge, DataView, Drawer, Popover, Banner, Tooltip, EmptyState, Skeleton, toast/decision host and guarded navigation should be reused. Keep the Health ID tokens and icon component; add missing code-native icons there, without another library.
- Sidebar and mobile navigation already share the same `items` array; workspace search receives that array. The dashboard separately recreates the catalogue as cards. The necessary change is to extract/extend the existing navigation model, not build a competing one.
- Prior verification covers 75 workspace/list/create cases at three widths, plus authentication and narrow layouts. This audit adds source-level coverage of the shared components and each module. It does not falsely claim every role/provider/state permutation has been manually viewed.

Companion deliverables: [route, state and component map](UI-SCREEN-MAP.md), [every module and its role coverage](UI-MODULE-AUDIT.md), [role/provider explanation](ROLE-PROVIDER-MATRIX.md), [all 112 matrix rows](ROLE-PROVIDER-MATRIX.csv), and [draft UI rules](UI-RULES.md).

## Exact label/icon issues

Use Home; Patients; Appointments; Patient visits (current Patient Journey); Nursing observations; Nursing tasks; Theatre & Procedures; Dispatch; Staff & access; Facility settings; Patient billing; Insurance & Claims; Supply; Facility subscription; External record access. These are proposed display labels, not enum/route migrations.

Preserve stored Health ID/MRN values; internal `hid-*`, `emr-*` CSS names and events are not user-facing brand text and do not need a dangerous global rename. Newly written copy uses Health ID and EHR. Examples requiring cleanup include `src/workflows.tsx` triage separators, `src/profiles.tsx` security-delivery sentence, and the replacement character in `src/service.ts` idle-period validation. The module audit records every current catalogue label/icon and its role coverage.

## Permission and architecture decisions

**No permissions changed by this audit.** Implementation would narrow provider-inapplicable navigation and route capability, not add role grants. Merged parents must be the union of accessible children, while each tab/action keeps its original permission. Search must scope patients/staff/results independently; the existing full local simulation authority is not a production data-access boundary.

Subscription is strictly Hospital Owner, Hospital Admin and Billing Officer. Cashier is not added. “Billing information” in the brief is interpreted as subscription/commercial facility data; existing authorized patient billing/payment duties remain available to Cashier. If all patient finance access was intended to change too, that is a separate permission decision.

The requested Owner/Admin bed-occupancy and broad clinical-workload widgets are **not** justified by current default clinical permissions. They require a restricted aggregate contract/permission, not access to raw clinical records. They remain omitted from the no-new-grants matrix until that aggregate scope is approved. Layout editing can never circumvent permission checks.

Real server-enforced subscription stripping and remote search authorization remain backend handover requirements. Frontend work includes appropriately projected mock responses and tests that forbidden payloads never reach ordinary UI adapters. It cannot establish actual server enforcement by hiding controls.

An API-free local aggregate widget can still have a loading boundary, but true independent remote widget loading needs defined query contracts. Reuse current service conventions and adapters rather than fake timers. Provider type normalization and safe update activation need explicit compatibility handling, not visual-only replacements.

## Proposed implementation sequence after approval

1. Canonical provider capability metadata and single navigation registry; preserve legacy links, permission checks and stable record IDs.
2. Requested Supply/Insurance tab merges and Settings grouping; keep additional clinical/people merges out of scope unless separately approved.
3. Top bar, avatar menu, bell, scoped search, quiet reserved connectivity area and configurable demo chip.
4. Shared role/provider dashboard widgets and empty states, followed by scoped pin/reorder/default-layout preferences.
5. All shared headers, filter controls, metadata and count labels; module-specific exceptions listed in the inventory.
6. Safe update notice; keyboard/accessibility, all-role/provider routing and data-projection regressions; responsive and state audit.

Acceptance will include current-route visibility after group collapse, keyboard avatar/menu operation, no duplicate same-event banners, one primary action per view, no connectivity overlap, finance-payload isolation, per-tab denial handling, scoped search/privacy, preference persistence and old-route redirects.
