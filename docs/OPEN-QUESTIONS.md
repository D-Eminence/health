These items are based on the `hid-system` snapshot at `c4b5445` and the
frontend integration in this repository. They separate known backend defects,
deployment dependencies and absent contracts. The historical
[gap map](./HEALTH_ID_COMPLETE_FRONTEND_GAP_MAP.md) contains the reference
screen audit; its baseline status column predates the portal implementation.

## Launch blockers found at hid-system `54f79d2` (2026-10-11)

Static trace of hid-system `main` at `54f79d2` against this repository's `main`
at `cd75a55`. None of these has been run against a deployed backend; the
backend needs to confirm each on a full local stack or staging.

| Item | Current evidence | Needed to close |
| --- | --- | --- |
| Patient-scoped reads refused for cookie sessions | EHR, OCR, Lab and Pharmacy authorize a patient read by calling Identity `POST /api/v1/identity/service/authorization/check`, forwarding the browser's cookie, `Origin` and `X-CSRF-Token` (ehr-api `integrations/identity-api.service.ts:43-57`, `common/request-context.ts:74-76`; `packages/api-client/src/identity.ts:138-150, 247-261`). Identity's global `SecurityGuard` treats that forwarded cookie on a `POST` as a browser mutation and requires an allowed `Origin` and a matching CSRF token (`auth/security.guard.ts:67-68, 286-303`). A same-origin browser `GET` carries neither, and the gateway passes `Origin` through unchanged, so by static trace these reads answer `403 ORIGIN_DENIED`. This covers encounters, clinical records, documents (list and download), the emergency summary and every OCR read of an existing job, and also hides the forms that depend on them. Writes carry `Origin` and CSRF and pass. No runtime verifier, test or browser run covers a cookie-session `GET` through this path. The frontend cannot fix it: `Origin` is a forbidden header. | Backend: authorize delegated reads without the cookie-mutation check (for example, check the caller's original method, which the workload identity can vouch for), keeping it for real mutations. Add an HTTP test: a same-origin cookie `GET` of `/api/v1/ehr/patients/:id/encounters` succeeds, and a cross-site write without CSRF is still refused. |
| OCR purpose of use | OCR requires `purpose: healthcare-operations` (`create-ocr-job.dto.ts:26` and the validation, confirmation and retry DTOs), and Identity matches a grant's purpose exactly (`postgres-identity.provider.ts:73`; migration 0012). The provider portal requests access only for `direct-care`, and PIN grants are `direct-care`, so no OCR job can be authorized from the portal. The backend accepts `healthcare-operations` access requests, but the patient's request list does not return the purpose (`consent.service.ts:113-118`), so a patient could not see that a request is for record import. | Product and backend decision: either align the OCR purpose with `direct-care`, or return the purpose to the patient and then add a purpose choice to the provider's access request. |
| OCR validation, confirmation and publication | hid-system's Stage 8 release blockers (`PHASE_4_STAGE_5_RELEASE_READINESS.md` §4.2, not fixed): the runtime role cannot take its own `FOR UPDATE` locks on `ocr.validations` and `ocr.patient_confirmations`, so these commands fail with `42501`; S4b cannot pass. No OCR HTTP or worker run against a database exists. D-Eminence/hid-system#34 (Phase 4 Stage 9, open, not merged) removes these locks and adds an OCR runtime verifier, which runs as the OCR runtime role against fakes of Identity, EHR and Lab using bearer tokens. Its evidence is local and synthetic. | Merge and deploy hid-system#34 and migration 0078, then the S4b staging run. |
| OCR review fields and failed publications | `validate()` checks only the domain; field rules run at publication, which marks the publication terminally `failed` (`ocr.service.ts:248, 474-541`). One publication is allowed per validation, and a failure caused by an owning-service outage is never classed as retryable (`:399-425, 532`), so the import is stranded. D-Eminence/hid-system#35 (stacked on #34, open) stores an owning-service failure other than a `4xx` as `OWNING_SERVICE_UNAVAILABLE`, which the claim retries after its backoff. The field rules are still checked only at publication. | Backend: merge hid-system#35 and enforce the publication field rules in `validate()`. Frontend: then offer a retry of a retryable publication. |
| Logout after an idle period | `POST /auth/logout` needs a live access token (15 minutes), while the refresh cookie lasts 8 hours (`auth.controller.ts:292-300, 366-380`). A sign-out after a longer idle was refused with `401`: the page signed out locally, but the server session stayed restorable from the browser. The patient portal now restores the session once and repeats the logout, only for the same patient (branch `claude/launch-readiness-fixes`); the provider portal's equivalent is in D-Eminence/Health-id#25. | Backend: let logout revoke by the refresh token and always clear the cookies. |
| Lab request changes after Lab accepts | `LabRequestsService.update()` changes status, priority and clinical information in EHR only (`lab-requests.service.ts:136-170`); it never calls Lab. Lab work items are written once, when Lab accepts the active order, and cannot be updated (migration 0018, `lab_work_items_immutable`). Cancelling or marking entered in error an active or on-hold request would leave Lab working on it. The clinical record therefore offers a status change only for a draft (cancel, mark entered in error) and tells the clinician to contact the laboratory for anything else. | Backend: pass a cancellation or entered-in-error change to Lab (or refuse it once Lab has accepted), with tests. Then the frontend can offer these changes. |
| Corrected vitals elsewhere | A vital is corrected by appending `ehr.vital_corrections`; the vital row keeps what was recorded and counts corrections in `current_correction_no` (`vitals.service.ts:153-200`). Nothing in hid-system reads corrections back except their own list: the patient's record aggregate returns the recorded values without `currentCorrectionNo` (`patient-records.service.ts:68-73`), so the patient portal shows superseded vitals with no sign of a correction. Nor does the backend define whether a correction replaces the whole set or only the values it names. The provider portal now shows the latest correction as the whole current set and the recorded values beneath it, and prefills a correction with the current set; if the correction cannot be read it says so and offers no further correction. | Backend: define the semantics, and return corrected values (or the correction number) from the patient aggregate and any export. Then the patient portal can show them. |
| Timeline pages skip rows within a millisecond | `timelinePage()` builds the next cursor from `new Date(sortAt).toISOString()`, which keeps milliseconds (`ehr/shared/clinical-context.ts:53`). The keys it pages over (`created_at` from `clock_timestamp()`, and client-supplied `started_at` / `recorded_at`) keep microseconds. The next page's predicate `(created_at, id) < (cursor ms, cursor id)` therefore excludes any row later than the truncated cursor within the same millisecond as the last row shown. For example, a last row at `.123456` gives a cursor of `.123`, so a row at `.123400` is never shown. This is likely only for records created in bulk or by import. Static trace; not run against a database. The clinical record now pages encounters and record lists, so it inherits this. | Backend: carry the full-precision key in the cursor (for example, `to_char` with microseconds or the epoch in microseconds), and add a test with rows that share a millisecond. |

| Lab execution list and result values | D-Eminence/hid-system#31 (merged into hid-system `main` as `158f68c`, post-merge CI passed; not deployed) makes `listForSpecimen()` resolve the specimen's patient and call the same Identity `read_records` authorization as `get()` before any execution or result is read: a refusal is `403 LAB_EXECUTION_ACCESS_DENIED`, an Identity failure fails closed, break-glass reads behave as for `get()`. Lab RLS applies the same consent check, so an absent or revoked grant normally returns `404 LAB_SPECIMEN_NOT_FOUND`. | Lab results when access cannot be verified | The portal now fails closed. With `lab.execution.read`, result values come from a successful execution-list read, or from the caller's own successful write until the next read; every failed list read removes the values already on screen, for every specimen of the accession. The message depends on the failure: 403 or 404 says access was denied; 401 says the session has ended and to sign in again; anything else (an Identity outage such as `503 IDENTITY_SERVICE_UNAVAILABLE`, another 5xx, a timeout, a network failure or cancellation, an unexpected error, or a 4xx answered on its merits) says access could not be verified. A refusal answered on its merits (400, 409, 412, 422, 429) and the history 404 for a never-released result change nothing. Every hide starts a new result generation for the accession at once, before any state changes, so a read or action answer that any specimen of the accession sent before the hide is discarded unapplied, and values from before the hide no longer render: component tests that record every React commit show no sibling value in any commit once the denial is on screen, whichever answers first. The portal never merges a Lab result or accession read with an identical one still in flight, so only a read sent after the hide can restore values. Component and API-client tests only; no browser, runtime or staging run. | Decide whether the panel should retry automatically after an outage instead of waiting for Refresh, and whether the unavailable message should name the cause (outage or network) without exposing server detail. Members with custom roles that can run executions but not read them lose sight of an execution after a transient failure until they refresh the accession; decide whether that is acceptable. The session-ended message asks the person to sign in again, but the staff app has no in-page route to sign-in after a mid-session 401 (an app-wide gap, not changed here); decide whether the panel should offer one. ## Reference workflows without an audited API

The following remain backend contract work before an operational frontend can
claim them:

- **Patient account:** general self-profile editing, patient-created sharing or
  invitations, and patient-authored structured history. Patient revocation of a
  grant the patient authorized, login/account deletion, and emergency contacts
  are wired to the hid-system Phase 3 contract (see
  [Phase 3 patient safety](PHASE_3_PATIENT_SAFETY.md)); revoking a workforce or
  break-glass grant remains outside patient authority.
- **Hospital operations:** appointments, triage queues, inpatient/ICU, maternity,
  surgery, radiology, claims and insurance, inventory, referrals, shifts/HR,
  quality, telemedicine, ambulance, blood bank, dental and procurement.
- **Provider organization:** facility staff invitation/membership mutations,
  branch selection, provider profile/credentials/presence and offline
  lease/sync/conflict handling.
- **Outreach:** public worker signup, OTP, invitation/join, visits and screenings.
  The staff-scoped campaign, member and registration-case routes are separate
  supported contracts and are wired in the provider portal.
- **Migrate:** bulk import, project matching, project/team lifecycle, a global
  completed-record index and intelligence analytics. OCR job, extraction,
  validation, patient confirmation and publication are supported routes.
  Patient confirmation and publication work under the least-privilege OCR
  runtime only from hid-system migration 0075 (D-Eminence/hid-system#30);
  before it, their outbox insert was refused. From migration 0076 a patient
  confirmation also needs a database owner that can read the source document
  (hid-system release checklist P8); otherwise it fails rather than accepting
  any patient. No staging run of the OCR pipeline exists yet (hid-system
  release checklist S4b).
- **Commercial/admin:** subscription, trial, invoice, payment and global AI
  processing administration. The existing public prices, demo intake and
  platform administration routes do not imply these capabilities.
- **Platform administration:** an organization directory, support cases or
  notes, security event metrics, legal holds and session-event review. The
  console lists these as unavailable (see
  [Phase 4 Stage 3](./PHASE_4_STAGE_3_ADMIN_CONSOLIDATION.md)).

Before adding any of these screens, agree a permissioned API with persistence,
validation and audit behavior in `hid-system`. Static reference UI and browser
fixtures do not resolve the missing contract.
