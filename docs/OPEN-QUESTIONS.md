# Open questions and integration blockers

These items are based on the `hid-system` snapshot at `c4b5445` and the
frontend integration in this repository. They separate known backend defects,
deployment dependencies and absent contracts. The historical
[gap map](./HEALTH_ID_COMPLETE_FRONTEND_GAP_MAP.md) contains the reference
screen audit; its baseline status column predates the portal implementation.

| Lab execution list and result values | D-Eminence/hid-system#31 (merged into hid-system `main` as `158f68c`, post-merge CI passed; not deployed) makes `listForSpecimen()` resolve the specimen's patient and call the same Identity `read_records` authorization as `get()` before any execution or result is read: a refusal is `403 LAB_EXECUTION_ACCESS_DENIED`, an Identity failure fails closed, break-glass reads behave as for `get()`. Lab RLS applies the same consent check, so an absent or revoked grant normally returns `404 LAB_SPECIMEN_NOT_FOUND`. The portal treats a 403 or 404 on a specimen's execution list as access ended: it shows an access-denied message and removes the result values of every specimen in that accession (one patient). With `lab.execution.read`, a 403 or 404 from a Lab action or history read reloads the list, so values stay only while reads are still authorized; without it the panel hides the values at once. A history 404 for a result that was never released is not treated as a refusal. Unit and component tests only. | Deploy the Lab API change, then verify in staging that a revoked grant hides result values in the provider portal. |
| Lab results when access cannot be verified | The portal now fails closed. With `lab.execution.read`, result values come from a successful execution-list read, or from the caller's own successful write until the next read; every failed list read removes the values already on screen, for every specimen of the accession. The message depends on the failure: 403 or 404 says access was denied; 401 says the session has ended and to sign in again; anything else (an Identity outage such as `503 IDENTITY_SERVICE_UNAVAILABLE`, another 5xx, a timeout, a network failure or cancellation, an unexpected error, or a 4xx answered on its merits) says access could not be verified. When completing, entering or correcting, verifying or releasing a result, starting an execution or reading result history fails with 401, 403, 404, 408, a 5xx, no response or an unexpected error, the panel reloads the list: a failed reload hides the values, a successful one keeps them (for example a break-glass reader who may read but not write). Without `lab.execution.read` there is no reload, so the panel hides at once. A specimen step (collect, receive, reject) that fails with such a status re-checks in place: the step keeps its error and what was typed into it, the accession is read again, and every panel re-reads its results (without `lab.execution.read` it hides at once); a failed accession read removes the whole accession. Refresh accession, or a recorded step, remounts every panel, which then reads its results once. A refusal answered on its merits (400, 409, 412, 422, 429) and the history 404 for a never-released result change nothing. Every hide starts a new result generation for the accession at once, before any state changes, so a read or action answer that any specimen of the accession sent before the hide is discarded unapplied, and values from before the hide no longer render: component tests that record every React commit show no sibling value in any commit once the denial is on screen, whichever answers first. The portal never merges a Lab result or accession read with an identical one still in flight, so only a read sent after the hide can restore values. The three hidden-state messages are fixed text with no server detail, result values or patient identifiers; the error of a failed action, step or history read still shows the service's problem message, as before. Component and API-client tests only; no browser, runtime or staging run. | Decide whether the panel should retry automatically after an outage instead of waiting for Refresh, and whether the unavailable message should name the cause (outage or network) without exposing server detail. Members with custom roles that can run executions but not read them lose sight of an execution after a transient failure until they refresh the accession; decide whether that is acceptable. A 401 that survives the client's refresh now ends the whole staff session (see "Staff session end"), so the workspace and this panel are replaced by the session-ended screen and its sign-in link; the panel's own session-ended message remains only as a fallback. Verify the behaviour in staging with a real Identity outage and an expired session. |

## Reference workflows without an audited API

The following remain backend contract work before an operational frontend can
claim them:

- **Patient account:** general self-profile editing, patient-created sharing or
  invitations, and patient-authored structured history. Patient revocation of a
  grant the patient authorized, login/account deletion, and emergency contacts
  are wired to the hid-system Phase 3 contract (see
  [Phase 3 patient safety](PHASE_3_PATIENT_SAFETY.md)); revoking a workforce or
  break-glass grant remains outside patient authority.
- **Hospital operations:** appointments, triage queues, inpatient/ICU, maternity,
  surgery, radiology, claims and insurance, inventory, referrals, shifts/HR,
  quality, telemedicine, ambulance, blood bank, dental and procurement.
- **Provider organization:** facility staff invitation/membership mutations,
  branch selection, provider profile/credentials/presence and offline
  lease/sync/conflict handling.
- **Outreach:** public worker signup, OTP, invitation/join, visits and screenings.
  The staff-scoped campaign, member and registration-case routes are separate
  supported contracts and are wired in the provider portal.
- **Migrate:** bulk import, project matching, project/team lifecycle, a global
  completed-record index and intelligence analytics. OCR job, extraction,
  validation, patient confirmation and publication are supported routes.
  Patient confirmation and publication work under the least-privilege OCR
  runtime only from hid-system migration 0075 (D-Eminence/hid-system#30);
  before it, their outbox insert was refused. From migration 0076 a patient
  confirmation also needs a database owner that can read the source document
  (hid-system release checklist P8); otherwise it fails rather than accepting
  any patient. No staging run of the OCR pipeline exists yet (hid-system
  release checklist S4b).
- **Commercial/admin:** subscription, trial, invoice, payment and global AI
  processing administration. The existing public prices, demo intake and
  platform administration routes do not imply these capabilities.
- **Platform administration:** an organization directory, support cases or
  notes, security event metrics, legal holds and session-event review. The
  console lists these as unavailable (see
  [Phase 4 Stage 3](./PHASE_4_STAGE_3_ADMIN_CONSOLIDATION.md)).

Before adding any of these screens, agree a permissioned API with persistence,
validation and audit behavior in `hid-system`. Static reference UI and browser
fixtures do not resolve the missing contract.
