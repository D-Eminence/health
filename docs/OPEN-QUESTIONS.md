| Staff session end | hid-system (`main` at `6b49a06`, as at `54f79d2`) answers an ended, expired or revoked staff session with a generic `401 AUTHENTICATION_REQUIRED` on every protected route (the wording varies by service), clears no cookie there, and gives staff clients no reason; there is no staff counterpart of `PLATFORM_SESSION_EXPIRED`/`REVOKED`. Once the browser has dropped the refresh cookie (at the idle or absolute limit, or after a sign-out in another tab) `/auth/refresh` answers `403 CSRF_VALIDATION_FAILED`, which the portal treats as the ended session it is. Every refresh rotates the session, so a request still refused with 401 after the client's refresh does not prove the session ended (another refresh may have rotated it under the retry): the provider portal then asks the server (`/auth/session`, restoring once with the refresh) and ends the workspace only when the server confirms the session is gone or now belongs to another account. From the refusal until that answer the workspace is locked: hidden and inert, with the open patient out of view, but kept as it was. A session the server still accepts gets it back unchanged; one the server cannot vouch for (no answer, or an answer without an account) stays locked with Try again and Sign out, and nothing is cleared. An ended session replaces the whole workspace with a fixed "Your session has ended" screen and a "Sign in again" link to `/provider/sign-in`; the open patient is cleared, the ended session's protected requests still in flight are cancelled (so the next session never shares one of its reads), and answers that arrive later from the ended session (a patient lookup, a facility switch, a sign-out, a refusal) change nothing in the next session and are never restored or repeated once it has ended. After sign-in the portal returns only to an exact provider workspace path (never a query, another origin or another app). A refresh that answers for another account (signed in from another tab, staff or patient) counts as an ended session: the refused request is not repeated as that account, a facility switch answered for another account is not adopted, and a sign-out whose restore finds another account's session does not revoke it. A request sent while the session-ended screen shows is never refreshed. Protected requests are sent only while the session is ready (in use, confirmed and unlocked): one made while the workspace is locked or being checked waits, and is cancelled, never sent, if that session ends meanwhile. Every attempt waits again as it is sent, including the HTTP client's own retry of a read after a backoff and its repeat of a request after a refresh. A step that follows another (an upload's storage PUT and `/complete`, opening a patient after a PIN check or emergency access, opening a downloaded document) checks again just before it acts, so none proceeds while the session is being checked or cannot be confirmed, or once another account is active. A document upload runs only within the session it started in: the storage PUT is cancelled with it, and neither the upload intent nor `/complete` is sent after it ends. These are checks in the portal; no released hid-system build refuses a `/complete` from another account with a write grant for the patient (hand-off A15). hid-system#59 (`f04079a`; merged into `main`, not released) lets only the account that created the upload intent complete it (`assertUploader` and `created_by = $6` in `document.service.ts` at `bbc6e89`). The workspace locks as soon as the page is hidden or left (`visibilitychange`, `pagehide`), keeping its work. A session that becomes ready while the page is already hidden (opened in the background, or signed in or restored while away) is locked from the start. A server answer that arrives while the page is hidden opens nothing, and a back/forward-cache restore reported while the page is still hidden is not a return. The lock is a React state change, committed just after the event, not inside it; whether a browser's snapshot can catch the page before it locks needs a real-browser check. Back in view within a minute, in the same session and with nothing heard meanwhile, it opens again without asking; after a minute or more, on a back/forward-cache restore, or once a session change was heard, it stays locked until the server confirms the session. A page that misses the event that brings it back opens on its next focus by the same rule, and an answer that arrives while the page is hidden does not open it. Tabs tell each other, naming no one, when they sign in, sign out or end, and the patient portal does the same when a patient signs in (password or Google) or signs out; a staff tab that hears it locks and asks the server. Announcing is best effort: in a browser that refuses the channel, only the announcement is lost, and sign-in, sign-out and the provider portal still work. The opening session check ignores its answer once a sign-in or sign-out has followed. A `403 PATIENT_SCOPE_DENIED` locks the workspace and asks the server, as a 401 does, and never ends the session on its own: Identity and EHR send it after verifying a valid patient session on a workforce route, so the browser's cookies now belong to a patient. Identity's patient-only Google link also sends it to a non-patient session, but the provider portal never calls that route. Calls under `/api/v1/auth/` (the facility switch included) do not report it. Any other 403, including a refused patient, facility, permission, emergency access, facility switch, CSRF or origin check, never locks or ends the session. Facility switching and sign-out restore a session whose 15-minute access token alone expired; sign-out reports success only once the server confirmed it or refused to restore the session, and otherwise says it could not be completed; signing in waits for a sign-out or refresh still in progress, either of whose answers can clear the session cookies. ## Reference workflows without an audited API

The following remain backend contract work before an operational frontend can
claim them:

- **Patient account:** general self-profile editing, patient-created sharing or
  invitations, and patient-authored structured history. Patient revocation of a
  grant the patient authorized, login/account deletion, and emergency contacts
  are wired to the hid-system Phase 3 contract (see
  [Phase 3 patient safety](PHASE_3_PATIENT_SAFETY.md)); revoking a workforce or
  break-glass grant remains outside patient authority. Hand-off F4 and E16;
  patient document download and released results are B6 and E15.
- **Hospital operations:** appointments, triage queues, inpatient/ICU, maternity,
  surgery, radiology, claims and insurance, inventory, referrals, shifts/HR,
  quality, telemedicine, ambulance, blood bank, dental and procurement
  (hand-off F1).
- **Provider organization:** facility staff invitation/membership mutations,
  branch selection, provider profile/credentials/presence and offline
  lease/sync/conflict handling (hand-off B3, E4, F2, F7).
- **Outreach:** public worker signup, OTP, invitation/join, visits and screenings
  (hand-off F6). Campaign and member reads and registration cases (create,
  list, link an existing patient) are wired in the provider portal. Campaign
  create, status change and add member are refused by Identity
  (`outreach.campaign.write` is not authorized: `authorize-outreach.dto.ts`,
  ADR-045), so the portal offers none of them and says "Campaign management is
  not yet available" (hand-off B10, E5).
- **Migrate:** bulk import, project matching, project/team lifecycle, a global
  completed-record index and intelligence analytics. OCR job, extraction,
  validation, patient confirmation and publication are supported routes.
  Patient confirmation and publication work under the least-privilege OCR
  runtime only from hid-system migration 0075 (D-Eminence/hid-system#30);
  before it, their outbox insert was refused. From migration 0076 a patient
  confirmation also needs a database owner that can read the source document
  (hid-system release checklist P8); otherwise it fails rather than accepting
  any patient. The runtime role's row locks are removed by
  D-Eminence/hid-system#34 (merged, not released). No staging run of the OCR
  pipeline exists yet (hid-system release checklist S4b; hand-off C2, D3).
  Bulk import, projects and the completed-record index are hand-off F5 and
  B12.
- **Commercial/admin:** subscription, trial, invoice, payment and global AI
  processing administration (hand-off F3). The existing public prices, demo
  intake and platform administration routes do not imply these capabilities.
- **Platform administration:** an organization directory, support cases or
  notes, security event metrics, legal holds and session-event review. The
  console lists these as unavailable (see
  [Phase 4 Stage 3](./PHASE_4_STAGE_3_ADMIN_CONSOLIDATION.md); hand-off F3).

Before adding any of these screens, agree a permissioned API with persistence,
validation and audit behavior in `hid-system`. Static reference UI and browser
fixtures do not resolve the missing contract.
