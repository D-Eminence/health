Its `BACKEND-HANDOVER.md` describes proposed contracts, not implemented hid-system routes. The HTML also holds fixture data and local state only. ## Backend gaps and integration dependencies

The `BACKEND GAP` rows cannot be presented as operational screens. For each group below, the expected workflow is the corresponding reference row above, frontend completion is **no**, and required backend work is a permissioned API or a fix to the existing route with persistence, validation, audit and tests. The frontend source is listed in the table. In particular:

- **Clinical operations:** appointments, triage queue, inpatient/ICU, maternity, surgery, radiology, claims/billing/insurance, inventory, referrals, shifts/HR, quality, telemedicine, ambulance and blood bank need domain contracts. Encounters, vitals, notes, diagnoses, prescriptions and lab requests are supported; the provider portal's clinical record (`/provider/clinical`) creates them, pages each list by the backend cursor, and changes or corrects them: encounter, note and prescription status, note revisions, vital corrections, diagnosis changes, and cancelling a draft lab request or marking it entered in error.
- **Patient account control:** general profile editing and self-service share/invite need patient-scoped APIs. Grant revocation (`POST /identity/me/consent-grants/:id/revoke`, patient-authorized grants only) and account deletion (`/identity/me/account-deletion`) exist and the patient portal uses them (Phase 3). Existing consent approve/deny and PIN APIs do not imply these rights.
- **Commercial:** price catalog exists; promotions/free periods, subscriptions, invoices and payments do not. `null` quote prices must never become fabricated amounts.
- **Outreach:** staff campaign and registration-case APIs exist. Public worker signup, login, OTP, invitations and join flows from `hid-1.0` have no replacement contract.
- **Migrate:** OCR job, extraction, validation and publication APIs exist. Bulk import, project matching, completed-record indexes, legacy project/team operations and the unmounted intelligence workspace have no backend contract.
- **Admin:** dashboard, principal, review, audit, pricing, demo and integrations exist. Global AI processing and billing administration do not.
- **Facility reporting:** The provider portal reads Identity facility audit events. The gateway's `/api/v1/audit/*` route shadows EHR's identically named audit controller, and no general provider reporting or trend API was found. Platform audit uses the separate admin route.
- **Hospital onboarding:** Dashboard's five-step registration and nine-step setup are simulated. The real application DTO only accepts product, organization type, CAC number, administrator name/email and Turnstile; completion adds a few company fields. Migration `0052_authoritative_cac_identity.sql` replaced the six-argument `identity.submit_organization_application` of `0046_organization_onboarding.sql` with the five-argument function that `organization-applications.service.ts` calls, so the submit route has no argument mismatch (already at `c4b5445`). Public-web `/provider/apply` links to the portal's `/provider/enroll`, which uses the self-service `/identity/provider-enrollments` routes, and public-web `/provider/complete` uses the completion routes. There is no server draft, department, branch, document, invitation, billing/trial or setup-progress contract. Extend the DTO and add those contracts before the reference steps can become a usable onboarding flow.
- **Provider patient registration:** Staff can review a known case UUID and perform backend-governed approval, linking, and enrollment. The backend has no case list/search and case detail omits account enrollment state, so resume after refresh cannot reliably show whether enrollment already happened. Starting new NIN cases is disabled in normal deployments until a verification provider is released.
- **Patient consent:** The patient list, approve and deny routes are `@PatientAllowed()` and `@FacilityOptional()` and act on the patient session, not `consentContext()`; the patient portal lists and decides requests (see the Access requests/consent row).
- **Emergency clinical access:** Identity can issue an audited break-glass grant, and EHR exposes a dedicated emergency record summary of completed encounters and signed notes. The ordinary EHR encounter, vital, note, diagnosis, prescription and lab-request controllers call `clinicalContext()`, which rejects `X-Purpose-Of-Use: emergency`. A detailed chart under an emergency grant therefore needs an explicit backend policy and route contract; the frontend must not silently retry it as `direct-care`.
- **Lab result visibility:** `LabExecutionsService.listForSpecimen()` now resolves the specimen's patient and calls the same Identity `read_records` authorization as the single-execution `get()` before it reads any execution or result revision (D-Eminence/hid-system#31, merged into hid-system `main` as `158f68c`; not deployed). Lab row-level security applies the same consent check, so an absent or revoked grant normally returns `404 LAB_SPECIMEN_NOT_FOUND`. Staging verification is still pending.
- **Staff session end:** hid-system gives an ended, expired or revoked staff session only a generic `401 AUTHENTICATION_REQUIRED` and no reason. Because every refresh rotates the session, the provider portal confirms a 401 with the server before acting. From the refusal until the server answers, the workspace is locked (hidden and inert); a session still accepted gets it back, one the server cannot vouch for stays locked. When the server confirms the end, the portal replaces the whole workspace with a fixed session-ended screen and a sign-in link, clears the open patient, cancels the ended session's protected requests in flight and never repeats or applies them in the next session. After sign-in it returns only to an exact workspace path. A refresh, facility switch or sign-out restore that answers for another account is treated as an ended session, uploads stop when their session ends, and the workspace locks as soon as the page is hidden, re-checking with the server after a minute away, on a back/forward-cache restore, or when another tab or the patient portal reports a session change. Protected requests and the steps that follow another (an upload's storage PUT and completion, opening a patient after a PIN check, opening a document) wait until the session is ready and are dropped if it ends. A `403 PATIENT_SCOPE_DENIED` makes the portal ask the server; no other 403 locks or ends the session. Refreshes, sign-ins (provider enrollment activation included) and sign-outs take turns across windows where the browser supports Web Locks, so two windows do not present the same refresh token and a sign-out's answer cannot clear another window's sign-in. A sign-out first confirms that the browser still holds this account's session (the provider portal when it had to wait, the patient portal always) and leaves alone another account signed in meanwhile. Sign-out from a locked workspace first confirms with the server that the cookies still carry this account's session; logout cannot yet be limited to that session. A document handed to OCR opens there only for the same account and facility, and only once. Whether hid-system refuses upload completion by an account other than the one that created the intent is unverified. Component tests only; no browser, runtime or staging run.
- **Offline and staff profiles:** Dashboard's offline lease, sync, conflict, duplicate review, staff presence, profile photo and credential review endpoints are proposed only. Its local simulation is not an implementation of these capabilities.

Known integration work in `hid-system` is outside this frontend branch: production auth cookies are host-only and Strict, so authenticated browser calls need a same-origin `/api/v1` proxy (the backend repository has a Cloudflare frontend-worker pattern). On a distinct origin, the Identity and Pharmacy CORS gaps (`DELETE`/`PATCH`, Pharmacy `x-csrf-token`) are fixed by hid-system Phase 4 Stage 5 (D-Eminence/hid-system#25). The Identity NIN provider is disabled by default pending its release/security gates. A live staging gateway URL, allowed frontend origins, Google client configuration and Turnstile site key are required for real acceptance; the user confirmed no staging environment exists yet. Patient enrollment activation returns an HID code but no session; the UI must lead the person through sign-in. The gateway routes `/api/v1/audit/*` to Identity, so EHR's identically named audit controller is not reachable through that route.
