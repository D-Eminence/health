The Health-id column and the BUILD, WIRE, REPLACE MOCK and IMPROVE actions record that baseline; rows marked BUILT record later work on `main`, and KEEP marks a baseline IMPROVE with nothing left to do. Last checked on 2026-10-12 against Health-id `main` with the six readiness PRs merged (Health-id #44, #42, #45, #46, #47 for the patient portal and #48 for admin and public; `main` at `0eda90f`) and against hid-system `main` at `6b49a06`, which does not contain `c4b5445`. hid-system `main` has since moved to `bbc6e89` (hid-system#48 to #53 and #55 to #62, merged on 2026-10-12, none released); rows those change say so. Rows that the hid-system alignment PR, Health-id #49 (merged as `cf32087` after Health-id #48) changed were checked on 2026-10-13 against its final code and hid-system `bbc6e89`. Backend work is cited by its id in the [backend hand-off](./BACKEND_OWNER_HANDOFF.md). This is an implementation inventory, not evidence of a staging release. The older open-tab pasted text describes a different backend PR and does not govern this frontend task.

`hid-system` uses an API-only gateway and `/api/v1` routes. Its cookie session, CSRF, facility, and purpose-of-use rules are authoritative. The baseline `Health-id` function-name endpoints and bearer-session assumptions described an older backend; `main` calls the registered `/api/v1` routes (`packages/contracts/src/registry.ts`) with cookie sessions. `Dashboard.zip` is a fictional local simulation whose own `FRONTEND-READINESS.md` says it is not ready for a real backend. Its `BACKEND-HANDOVER.md` describes proposed contracts, not implemented hid-system routes. The HTML also holds fixture data and local state only. Both sources provide workflow and UI references, never API authority.

## Backend gaps and integration dependencies

The `BACKEND GAP` rows cannot be presented as operational screens. For each of those, the expected workflow is the corresponding reference row above, frontend completion is **no**, and required backend work is a permissioned API or a fix to the existing route with persistence, validation, audit and tests. The other groups below (patient consent, facility reporting, lab result visibility, staff session end, admin) describe frontend work that is done and name what it still depends on. The frontend source is listed in the table, and the hid-system work is in the [backend hand-off](./BACKEND_OWNER_HANDOFF.md). In particular:

- **Clinical operations:** appointments, triage queue, inpatient/ICU, maternity, surgery, radiology, claims/billing/insurance, inventory, referrals, shifts/HR, quality, telemedicine, ambulance and blood bank need domain contracts (hand-off F1, F2). Encounters, vitals, notes, diagnoses, prescriptions and lab requests are supported; the provider portal's clinical record (`/provider/clinical`) creates them, pages each list by the backend cursor, and changes or corrects them: encounter, note and prescription status, note revisions, vital corrections, diagnosis changes, and cancelling a draft lab request or marking it entered in error; since the hid-system alignment PR, for a role holding `lab.work-item.accept`, also activating a draft or resuming a held request, each sent to Lab, and sending a saved active request again. EHR does not pass an encounter or prescription change on to Pharmacy or Lab, or a hold, cancellation, completion or entered in error of a lab request Lab has accepted (hand-off A1, A3), so the record warns at those forms and offers no such lab-request change. On hid-system `main` (not released) Pharmacy refuses to dispense a prescription no longer active at the version it accepted (hid-system#48), and EHR sends a lab request left active to Lab (hid-system#56).
- **Patient account control:** general profile editing and self-service share/invite need patient-scoped APIs (hand-off F4, E16). Grant revocation (`POST /identity/me/consent-grants/:id/revoke`, patient-authorized grants only) and account deletion (`/identity/me/account-deletion`) exist and the patient portal uses them (Phase 3). Existing consent approve/deny and PIN APIs do not imply these rights. Patients cannot download their documents or see released lab results (hand-off B6, E15).
- **Commercial:** price catalog exists; promotions/free periods, subscriptions, invoices and payments do not (hand-off F3). `null` quote prices must never become fabricated amounts.
- **Outreach:** staff campaign and member reads and the registration-case APIs work. Campaign writes answer `400 VALIDATION_FAILED` on hid-system `main` (ADR-045), and the portal offers none (hand-off B10, E5). Cookie reads need D-Eminence/hid-system#43 (`26e8145`), merged but not released. Public worker signup, login, OTP, invitations and join flows from `hid-1.0` have no replacement contract (hand-off F6).
- **Migrate:** OCR job, extraction, validation and publication APIs exist. A publication that failed transiently resumes only by replaying its original Idempotency-Key from the same account, and the portal holds that key in page memory only; there is no resume-by-id route or worker (hand-off B5). There is no facility job list (B12), and the portal cannot obtain the purposes OCR requires (B4, E3). Bulk import, project matching, completed-record indexes, legacy project/team operations and the unmounted intelligence workspace have no backend contract (F5).
- **Admin:** dashboard, principal, review, audit, pricing, demo and integrations exist. Global AI processing and billing administration do not (hand-off F3).
- **Facility reporting:** The provider portal reads Identity facility audit events. The gateway sends `/api/v1/audit/*` to Identity, and EHR's audit controller of the same name is not registered in any EHR module (hand-off E14). No general provider reporting or trend API was found (F2). Platform audit uses the separate admin route.
- **Hospital onboarding:** Dashboard's five-step registration and nine-step setup are simulated. The real application DTO only accepts product, organization type, CAC number, administrator name/email and Turnstile; completion adds a few company fields. Migration `0052_authoritative_cac_identity.sql` replaced the six-argument `identity.submit_organization_application` of `0046_organization_onboarding.sql` with the five-argument function that `organization-applications.service.ts` calls, so the submit route has no argument mismatch (already at `c4b5445`). The frontend no longer has a form for that route. Public-web `/provider/apply` links to the portal's `/provider/enroll`, which uses the self-service `/identity/provider-enrollments` routes, and public-web `/provider/complete` uses the completion routes. An onboarded organization gets only `org_admin`, with no clinical role and no way to add staff (hand-off B3, E4). There is no server draft, department, branch, document, invitation, billing/trial or setup-progress contract (F2). Extend the DTO and add those contracts before the reference steps can become a usable onboarding flow.
- **Provider patient registration:** Staff can review a known case UUID and perform backend-governed approval, linking, and enrollment. The backend has no case list/search and case detail omits account enrollment state, so resume after refresh cannot reliably show whether enrollment already happened (hand-off B8). Starting new NIN cases is disabled in normal deployments until a verification provider is released (B9).
- **Patient consent:** The patient list, approve and deny routes are `@PatientAllowed()` and `@FacilityOptional()` and act on the patient session, not `consentContext()`; the patient portal lists and decides requests (see the Access requests/consent row). It sends no `X-Purpose-Of-Use` on them: at hid-system `6b49a06` no guard, gateway rule or service reads that header there, and only the audit interceptor recorded it (hand-off A17).
- **Emergency clinical access:** Identity can issue an audited break-glass grant, and EHR exposes a dedicated emergency summary of this facility's completed encounters and signed notes, plus its vitals, diagnoses, prescriptions, lab requests and documents. The portal shows the last four only to a role holding each read permission and leaves out vitals, which EHR sends uncorrected (hand-off A11); since the hid-system alignment PR it also reads hid-system#52's `withheld`, `limits` and `truncated`. On a database built from hid-system's migrations the `emergency` purpose of use is not seeded, so break-glass itself is refused (hand-off B14). The ordinary EHR encounter, vital, note, diagnosis, prescription and lab-request controllers call `clinicalContext()`, which rejects `X-Purpose-Of-Use: emergency`. A detailed chart under an emergency grant therefore needs an explicit backend policy and route contract (hand-off B1, E1); the frontend must not silently retry it as `direct-care`.
- **Lab result visibility:** a clinician reads the released results of the Lab work item accepted from an EHR lab request through `GET /api/v1/lab/ehr-orders/:sourceEhrOrderId/released-results` (hid-system#51, merged, not released), which the clinical record and the emergency summary offer since the hid-system alignment PR; patients still see none (hand-off B6, E15). `LabExecutionsService.listForSpecimen()` now resolves the specimen's patient and calls the same Identity `read_records` authorization as the single-execution `get()` before it reads any execution or result revision (D-Eminence/hid-system#31, merged into hid-system `main` as `158f68c`; not deployed). Lab row-level security applies the same consent check, so an absent or revoked grant normally returns `404 LAB_SPECIMEN_NOT_FOUND`. Staging verification is still pending (hand-off C2, D3).
- **Staff session end:** hid-system gives an ended, expired or revoked staff session only a generic `401 AUTHENTICATION_REQUIRED` and no reason (hand-off B7, E6), except a sign-in made without an authenticator, which hid-system#71 (not deployed) refuses on every guarded route with `403 STAFF_MFA_REQUIRED` and whose refresh it ends. Because every refresh rotates the session, the provider portal confirms a 401 with the server before acting. From the refusal until the server answers, the workspace is locked (hidden and inert); a session still accepted gets it back, one the server cannot vouch for stays locked. When the server confirms the end, the portal replaces the whole workspace with a fixed session-ended screen and a sign-in link, clears the open patient, cancels the ended session's protected requests in flight and never repeats or applies them in the next session. After sign-in it returns only to an exact workspace path. A refresh, facility switch or sign-out restore that answers for another account is treated as an ended session, uploads stop when their session ends, and the workspace locks as soon as the page is hidden, re-checking with the server after a minute away, on a back/forward-cache restore, or when another tab or the patient portal reports a session change. Protected requests and the steps that follow another (an upload's storage PUT and completion, opening a patient after a PIN check, opening a document) wait until the session is ready and are dropped if it ends. A `403 PATIENT_SCOPE_DENIED` or `403 STAFF_MFA_REQUIRED` makes the portal ask the server, and the latter at load goes through refresh to the sign-in page; the session-ended screen and the sign-in page then say Health ID now asks for an authenticator code. No other 403 locks or ends the session, and a 503 never does. Refreshes, sign-ins (provider enrollment activation included) and sign-outs take turns across windows where the browser supports Web Locks, so two windows do not present the same refresh token and a sign-out's answer cannot clear another window's sign-in. A sign-out first confirms that the browser still holds this account's session (the provider portal when it had to wait, the patient portal always) and leaves alone another account signed in meanwhile. Sign-out from a locked workspace first confirms with the server that the cookies still carry this account's session; logout cannot yet be limited to that session (hand-off B7). A document handed to OCR opens there only for the same account and facility, and only once. No released hid-system build refuses upload completion by another account with a write grant for the patient (hand-off A15); hid-system#59 (`f04079a`, merged, not released) lets only the account that created the upload complete it. Component tests only; no browser, runtime or staging run.
- **Offline and staff profiles:** Dashboard's offline lease, sync, conflict, duplicate review, staff presence, profile photo and credential review endpoints are proposed only (hand-off F2, F7). Its local simulation is not an implementation of these capabilities.

Known integration work in `hid-system` is outside this frontend branch: production auth cookies are host-only and Strict, so authenticated browser calls need a same-origin `/api/v1` proxy (the backend repository has a Cloudflare frontend-worker pattern; hand-off D1). On a distinct origin, the Identity and Pharmacy CORS gaps (`DELETE`/`PATCH`, Pharmacy `x-csrf-token`) are fixed by hid-system Phase 4 Stage 5 (D-Eminence/hid-system#25). The Identity NIN provider is disabled by default pending its release/security gates (hand-off D5). A live staging gateway URL, allowed frontend origins, Google client configuration and Turnstile site key are required for real acceptance (hand-off D2 to D4); the user confirmed no staging environment exists yet. Patient enrollment activation returns an HID code but no session; the UI must lead the person through sign-in. The gateway routes `/api/v1/audit/*` to Identity; EHR's audit controller of the same name is not registered in any EHR module, so it is not served at all.
